## 1. Why it's broken — root causes

### 1a. HEAD does not typecheck → Vercel cannot deploy it

`npx tsc --noEmit` fails with **3 errors**, all committed at HEAD:

| File | Error |
|---|---|
| `src/components/routing/AppStartupNavigator.tsx:51` | TS2367: `decision?.reason === "onboarding_required"` — `"onboarding_required"` no longer exists on `GateReason` |
| `src/hooks/useStartupNavigation.ts:32` | TS2367: same dead comparison |
| `src/server/hono/routes/work-orders.ts:1286` | TS2552: `createSupabaseAnonServerClient` is not imported (it exists in `@/lib/supabase` but the import line only brings in `createSupabaseAdminClient`) |

**How it happened:** Commit `f5f37dbd2` (Oct 2, "Sunset business onboarding", PR #99) narrowed `GateReason` in `src/hooks/useAppAccessGate.ts` from `"ok" | "unauthenticated" | "onboarding_required"` to `"ok" | "unauthenticated"` but did not update the two consumers still comparing against `"onboarding_required"`. The work-orders import was dropped in the Hono migration.

**Impact:** `next.config.ts` does **not** set `typescript.ignoreBuildErrors`, so `next build` fails. Every Vercel deployment triggered from Oct 2 onward fails at build time. **Production is frozen on the last successful build** (pre-Oct-2). Nothing pushed since Oct 2 has reached users — including any fixes.

### 1b. The API 500 was a malformed probe, not (necessarily) a dead API

The observed `GET /api/v1/appointments/<uuid>` → 500 was fetched with **no `workspace_id` query param and no `Authorization` header**. Trace through `app/api/v1/appointments/[id]/route.ts`:

1. UUID parses fine → enters the `try` block.
2. `z.string().uuid().parse(searchParams.get("workspace_id"))` → `parse(null)` throws `ZodError`.
3. `errorResponse()` in `src/server/api.ts` has no branch for `ZodError` → falls through to the generic 500 (`{ code: "internal_error" }`).

So the 500 is **the expected response to that specific malformed request**. It does not prove the API is down. However, it exposes a real bug:

> **Bug:** `errorResponse` maps `ZodError` (a client input error) to HTTP 500. It should be 400. Every validation failure across all 66+ route handlers currently returns 500, which masks real client errors and pollutes error monitoring.

### 1c. The stuck "Loading..." — no timeout anywhere in the request path

For tenant subdomains (`momsoilchange.servicewriter.xyz`), `src/App.tsx` renders:

```tsx
{tenantLoading || startupBlocking ? (
  <LoadingScreen message={... "Loading..."} />
) : ( <Routes>... )}
```

`tenantLoading` comes from `TenantContext` → `fetchTenantProfile(slug)` → `apiClient.get('/v1/public-booking/momsoilchange?section=profile')`.

**`src/lib/api-client.ts` has no timeout.** `apiRequest()` calls bare `fetch()` with no `AbortSignal` timeout. If the API route hangs (slow Supabase, stalled serverless function, dropped connection), the promise never settles, `TenantContext` stays `loading: true` forever, and the user stares at "Loading..." indefinitely with no error and no retry. The only recovery is a manual refresh.

The "Offline mode" badge comes from `OfflineStatusBanner` (`src/components/offline/OfflineStatusBanner.tsx:118`), which renders when `navigator.onLine === false`. On a real device this means actual connectivity loss; combined with the stuck loader it produces exactly the reported screen.

### 1d. The service-role key is a single point of failure for 20 routes

`createSupabaseAdminClient()` (`src/lib/supabase.ts`) throws `Missing required environment variable: SUPABASE_SERVICE_ROLE_KEY` when the key is absent. **20 route files** call it, including:

- `app/api/v1/public-booking/[slug]/route.ts` (the tenant-profile path — the one the loading screen waits on)
- `app/api/v1/public-booking/[slug]/confirmation/route.ts`
- `app/api/v1/invitations/*` (4 files)
- `app/api/v1/dispatch/*`, `app/api/v1/payments/stripe-direct/*`, plus Hono routers

If `SUPABASE_SERVICE_ROLE_KEY` is missing from the Vercel production environment, all of these return 500. The client-side code has hardcoded canonical fallbacks (URL + publishable key for `rjfbrfognxqkyhdrpibx`), so the SPA shell loads and *looks* alive while every admin-keyed API call fails underneath it. **Vercel env vars could not be verified from this audit** — this must be checked in the Vercel dashboard.

## 5. Top 5 risks

1. **Undeployable HEAD.** Typecheck failures freeze production on a stale build. No fix — however urgent — can ship until this is resolved. (Effort: 0.5 hr)
2. **No request timeouts.** One hung API call permanently bricks the UI behind `LoadingScreen` with no error or retry. This is the most likely mechanism for the reported stuck screen. (Effort: 2 hrs)
3. **20 admin-keyed routes share one env var.** A missing/rotated `SUPABASE_SERVICE_ROLE_KEY` silently 500s public booking, invitations, dispatch, and payments while the SPA shell looks alive. (Effort: 0.5 hr to verify; monitoring thereafter)
4. **Test suite in free fall.** 47 failing tests across booking, dispatch, billing, fleet, and auth mean regressions ship undetected. The Oct 1–2 wave proves merges are not gated on green. (Effort: 1–3 days to triage; 2–4 hrs to add gating)
5. **Authorization rests on RLS + browser client for most reads.** 360 files hit Supabase directly from the browser; the August audit flagged permissive RLS policies and `SECURITY DEFINER` RPCs executable by `anon`. The Hono migration does not change this — it only moves *some* routes server-side. Any RLS misconfiguration is a tenant-isolation incident. (Effort: ongoing; needs the adversarial RLS review the August audit recommended)
